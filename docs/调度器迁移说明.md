# 调度器迁移说明（阶段 5）

> 目的：把 Jeremy 现有 16 个 cron（OpenClaw 定时任务）里属于 **A股侧** 的任务，
> 迁移进 `packages/scheduler`，做成「声明式任务 + 执行器 + 断点续跑 + 盘后 ETL」，
> 解决「约 8 个 cron 最近在 15 分钟硬超时打满」的痛点。美股侧本阶段不迁，
> 但框架已留好扩展位。

---

## 0. 现状与痛点

现有 16 个 cron 是 **OpenClaw agentTurn 任务**（不是系统 crontab），大部分
`timeoutSeconds: 900`（15 分钟硬超时）。约 8 个最近报 `error`，其中多数的
`lastErrorReason: timeout`、耗时 900~1141s 打满：

| 旧 cron | 超时 | 本阶段 |
|---|---|---|
| 财经快讯采集 | 926s timeout | 不迁（web_search 新闻采集，非策略） |
| 美股盘中监测 | 928s timeout | 不迁（美股） |
| 美股收盘监测 | 1141s timeout | 不迁（美股） |
| 美股 RSI+PEG | 1017s timeout | 不迁（美股） |
| 周度板块资金小总结 | error | **迁**（→ 盘后 ETL 每日化 + 周报） |
| 每周对冲评估 | error | 不迁（美股宏观） |
| 偷涨型每周扫描 | error | **迁**（→ 每日全市场扫描，每日化） |
| 美债收益率曲线周检 | error | 不迁（美股宏观） |

**超时的根因**：旧 cron 是「一个 agent 跑一个裸脚本」，超时被 OpenClaw 一刀切杀掉，
**没有部分结果、没有断点续跑**。长任务（全市场扫描 ~69s、回测几十分钟）一旦
碰上网络抖动或数据变多，就整体失败，下次从头再来。

## 1. 新架构：`packages/scheduler/`

```
packages/scheduler/scheduler/
  models.py       JobSpec（声明式任务定义）/ RunRecord（执行记录）/ JobResult
  cron.py         croniter 封装（时区固定 Asia/Shanghai，下次执行时间）
  registry.py     JobRegistry（按名查找 / 列出）
  repository.py   执行记录仓储（InMemory / MySQL）
  notifier.py     Notifier（FileNotifier / WebhookNotifier，可插拔）
  sharding.py     分片断点续跑状态（ShardTracker）
  executor.py     执行器（超时优雅中断 / 指数退避重试 / 并发跳过 / 进度上报）
  scheduler.py    编排层（list_jobs / trigger / run_due / list_runs）
  cli.py          命令行入口（list / run / loop）
  jobs/
    akshare_client.py  AKShare 数据客户端（策略层不 import）
    etl.py             板块 / ETF 资金流、ST 快照任务函数
    etl_repository.py  ETL 落库仓储（InMemory / MySQL）
    sinks.py           选股信号落库（strategy_scan_results 表）
    a_share.py         A股任务函数（每日扫描 / 每日报告 / 周度衰减）
    registry.py        A股任务注册表 + 调度栈组装
```

关键设计（对应任务书）：

- **声明式任务**：`JobSpec` 用 pydantic 描述一个任务（名称 / cron / 执行目标 /
  超时 / 重试 / 输出渠道 / 是否允许并发）。
- **执行器**：`JobExecutor.run` 在守护线程里跑任务，`thread.join(timeout)` 协作式
  超时；超时先 `request_stop()` + 宽限期让任务自己收尾，记录已完成部分，而非整体失败。
- **重试**：失败按 `max_retries` 指数退避（`backoff = base * 2^attempt`）；超时不重试。
- **并发控制**：`allow_concurrent=False` 时上次没跑完就跳过，记一条 `skipped`。
- **分片续跑**：把标的宇宙分片，每片独立 `mark_done`，中断后下次只跑未完成的片。
- **进度上报**：任务通过 `ctx.report_progress(pct, note)` 写进执行记录，前端能看到。

## 3. 超时问题怎么解决的

1. **每个任务声明自己的超时预算**（`JobSpec.timeout_seconds`），不再是统一的
   15 分钟硬超时。`daily_scan` 1200s、`weekly_decay_check` 1800s、`post_market_etl`
   600s，各按实际耗时定。
2. **超时优雅中断**：执行器 `thread.join(timeout)` 超时后先 `request_stop()`，
   给 2s 宽限期让任务在片间 / 循环间检查 `should_stop()` 并返回「已完成部分」的
   摘要；记录 `status=timeout` + 已上报的进度，**不是整个失败**。
3. **分片 + 断点续跑**：全市场扫描把 ~5510 只个股按 `shard_size=500` 分成若干片，
   每片完成后 `mark_done`。中断后下次 `daily_scan` 跳过已完成的分片，只跑未完成的。
   实测见第 6 节。
4. **失败重试**：`post_market_etl` / `daily_scan` 配了 `max_retries=1`，网络抖动
   自动退避重试一次。
5. **进度可见**：执行记录带 `progress`，前端 `/scheduler` 页能看到跑到百分之几。

## 4. 盘后 ETL 落库结构

| 表 | 用途 | 关键列 |

## 5. 报告输出（可插拔 notifier）

- `Notifier` 抽象接口；两个实现：
  - `FileNotifier`：写 Markdown 到 `STOCK_SCHEDULER_REPORT_DIR`（默认
    `~/Desktop/stock-platform/reports/`），文件名 `{任务名}-{时间戳}.md`。
  - `WebhookNotifier`：POST 到 `STOCK_FEISHU_WEBHOOK_URL`（飞书自定义机器人
    text 格式），超长自动截断。
- 飞书 webhook URL **从 `.env` 读，绝不硬编码**，`.env.example` 只放占位符。
- 每个任务在 `JobSpec.notifier` 声明渠道：`daily_report` / `weekly_decay_check`
  走 webhook（推飞书），`daily_scan` / `post_market_etl` / `st_snapshot` 走 file
  （留本地存档）。

## 6. 分片断点续跑实测

用 8 只个股、`shard_size=3`（=3 片）模拟「中断 → 续跑」：

```
第一轮: 扫描已中断：完成 2/3 片
  已完成分片: [0, 1]
  第一轮实际读取: [600000~600002], [600003~600005]
第二轮: 全市场扫描完成：3/3 片
  第二轮实际读取: [600006, 600007]     ← 只读未完成的第 3 片
  最终已完成分片: [0, 1, 2]
```

**结论：第二轮只读取了第 3 片（600006/600007），前两片被 `ShardTracker` 跳过，
断点续跑生效。** 单测 `tests/unit/test_scheduler_sharding.py` 锁死此行为。

## 7. 从旧 cron 切换过来的步骤清单（重点）

> 原则：**先并行跑，等他确认再切**，不要一刀切停旧 cron。

### 第 1 步：准备环境

```bash
cd ~/Desktop/stock-platform
# 1.1 建 .env（不要提交，.gitignore 已忽略）
cp .env.example .env
# 编辑 .env，至少填：
#   STOCK_HSJDAY_ROOT=~/Desktop/每日复盘/hsjday
#   STOCK_FEISHU_WEBHOOK_URL=https://open.feishu.cn/open-apis/bot/v2/hook/xxxx  ← 飞书机器人地址
#   STOCK_MYSQL_HOST/PORT/USER/PASSWORD/DB                                  ← 本地 MySQL 连接

# 1.2 装依赖（含新增 stock-scheduler）
make install
```

### 第 2 步：起数据库 + 应用 0004 migration

```bash
docker compose up -d mysql     # 若 MySQL 已在跑则跳过
# 首次启动会自动按序执行 migrations/；若 MySQL 是「已有数据」的老库，
# 手动执行 0004：
mysql -h127.0.0.1 -ustock -pstock stock_platform < apps/api/migrations/0004_scheduler_runs.sql
```

### 第 3 步：单跑一次验证（不触发调度）

```bash
.venv/bin/python -m scheduler.cli list               # 列出 5 个任务 + 下次执行时间
.venv/bin/python -m scheduler.cli run post_market_etl  # 先跑 ETL（验证 akshare + 落库）
.venv/bin/python -m scheduler.cli run daily_scan       # 再跑全市场扫描（验证分片 + 落库）
.venv/bin/python -m scheduler.cli run daily_report     # 验证报告生成 + 飞书推送
```

确认：`reports/` 目录出现 Markdown、MySQL 的 `sector_fund_flow`/`etf_fund_flow`/
`strategy_scan_results` 有数据、飞书收到推送。

### 第 4 步：起常驻调度循环（先并行，旧 cron 不停）

```bash
# 方式 A（推荐，最简单）：前台/后台跑进程内循环
.venv/bin/python -m scheduler.cli loop --interval 60

# 方式 B：挂到系统 crontab / launchd（开机自启），每分钟探活一次并拉起 loop
```

> 这时新平台和旧 cron **并行跑**，两边都在产生报告。对比 1~2 周，确认新平台
> 的扫描结果 / ETL 数据 / 报告内容正确。

### 第 5 步：停掉被替代的旧 cron（确认后）

在 OpenClaw 里 **禁用**（不要删除，可随时回滚）这 5 个旧任务：

1. 每日短线选股TOP5
2. ETF连续吸筹追踪（晚上8点）
3. 周度板块资金小总结
4. 月度板块资金大总结
5. 偷涨型每周扫描

**保留**其余 11 个（美股 / 宏观 / 新闻 / Obsidian 学习 / NVDA 周跟踪等）。

### 第 6 步：日常查看

- 浏览器打开前端 `/scheduler` 页（任务列表 + 执行历史 + 手动触发 + 失败高亮）。
- 或 `openclaw` 里用 `openclaw cron list` 看旧任务（切完后只剩美股侧）。
